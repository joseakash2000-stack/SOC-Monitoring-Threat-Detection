# SOC Investigation Workflow

This document describes the investigation workflow used in the lab for Suricata security alerts ingested into Splunk. The workflow is designed around an SOC L1 analyst process: validate the alert, establish context, enrich the detection, investigate related activity, classify the threat, and escalate when required.

## 1. Alert Intake

Alerts are generated by Suricata and forwarded into Splunk for centralized analysis.

Primary search scope:

```spl
index=main sourcetype=suricata
```

The analyst first confirms the alert timestamp, signature, source, destination, protocol, and destination port.

## 2. Alert Validation

Validate the detection by searching for the specific signature:

```spl
index=main sourcetype=suricata
| search alert.signature="<SIGNATURE>"
```

For broader investigation, wildcard matching can be used for a known vulnerability or attack family:

```spl
index=main sourcetype=suricata
| search alert.signature="*CVE-2020-3452*"
```

The objective is to establish whether the event is isolated, repeated, or part of a larger activity pattern.

## 3. Threat Enrichment

The project uses `suricata_threat_lookup.csv` to enrich Suricata signatures with SOC severity, CVSS, CVE information, MITRE ATT&CK mappings, threat category, and response recommendations.

Example:

```spl
index=main sourcetype=suricata
| lookup suricata_threat_lookup.csv signature as alert.signature OUTPUT soc_severity cvss cve mitre_tactic mitre_technique mitre_id threat_category recommendation
| eval soc_severity=mvindex(soc_severity,0)
| eval cvss=mvindex(cvss,0)
| eval cve=mvindex(cve,0)
| eval mitre_tactic=mvindex(mitre_tactic,0)
| eval mitre_technique=mvindex(mitre_technique,0)
| eval mitre_id=mvindex(mitre_id,0)
| eval threat_category=mvindex(threat_category,0)
| eval recommendation=mvindex(recommendation,0)
```

`mvindex(...,0)` is used to select the first value when lookup extraction produces a multivalue result.

## 4. Context Analysis

Review the network context associated with the alert:

```spl
| eval src_ip=mvindex(src_ip,0)
| eval dest_ip=mvindex(dest_ip,0)
| eval dest_port=mvindex(dest_port,0)
| table _time alert.signature soc_severity cvss cve mitre_tactic mitre_technique mitre_id threat_category src_ip dest_ip dest_port recommendation
| sort - _time
```

Key questions for an L1 analyst:

- Who is the source?
- What system is being targeted?
- Which service or port is involved?
- Is the source internal or external?
- Is the activity repeated?
- Are other alerts associated with the same source or destination?
- Is there evidence of successful exploitation or authentication?

## 5. Correlation and Scope

Investigate related activity using the source IP:

```spl
index=main sourcetype=suricata
| search src_ip="<SOURCE_IP>"
| stats count by alert.signature dest_ip dest_port
| sort - count
```

Investigate the targeted host:

```spl
index=main sourcetype=suricata
| search dest_ip="<DESTINATION_IP>"
| stats count by alert.signature src_ip dest_port
| sort - count
```

This helps determine whether the event is a single detection or part of a broader attack pattern.

## 6. Severity-Based Triage

The lookup classification is used to prioritize investigation.

### Critical

Immediate investigation. Look for evidence of exploitation, successful access, credential compromise, or impact. Escalate confirmed or suspected compromise according to the incident-response process.

### High

Prioritize investigation and establish whether the activity targeted a vulnerable or sensitive system.

### Medium

Validate context and determine whether the activity represents legitimate administration, security testing, reconnaissance, or suspicious behavior.

### Low / Informational

Review context and correlate with other activity. Many low-severity events may be benign or informational when viewed in isolation.

## 7. Investigation Examples

### Drupal SQL Injection

Signature:

```text
ET EXPLOIT Possible CVE-2014-3704 Drupal SQLi attempt URLENCODE 1
```

Key investigation points:

- Validate the targeted web server.
- Review web and application logs.
- Search for repeated attempts from the same source.
- Determine whether exploitation succeeded.
- Escalate if compromise is suspected.

MITRE ATT&CK mapping in the project: **T1190 — Exploit Public-Facing Application**.

### Cisco ASA / Firepower Path Traversal

Signature family:

```text
CVE-2020-3452
```

Key investigation points:

- Identify the affected device.
- Review firewall/device logs.
- Check for repeated attempts.
- Determine whether sensitive configuration or files were accessed.
- Escalate suspected compromise.

MITRE ATT&CK mapping in the project: **T1190 — Exploit Public-Facing Application**.

### Nmap Network Scanning

Signature:

```text
ET SCAN Possible Nmap User-Agent Observed
```

Key investigation points:

- Identify the scanning source.
- Review targeted systems and ports.
- Determine whether the scanner is authorized.
- Correlate with other reconnaissance activity.
- Escalate unauthorized or suspicious scanning.

MITRE ATT&CK mapping in the project: **T1046 — Network Service Discovery**.

### SSH Brute Force

Signature:

```text
SOC DEMO - SSH Brute Force
```

Key investigation points:

- Identify the attacking source and targeted host.
- Review SSH authentication logs.
- Look for successful authentication after failed attempts.
- Identify targeted accounts where available.
- Correlate the source with other alerts.
- Block or contain the source if malicious and authorized.
- Escalate suspected account or host compromise.

MITRE ATT&CK mapping in the project: **T1110 — Brute Force**.

## 8. Escalation Criteria

Escalate the alert when investigation identifies one or more of the following:

- Successful exploitation
- Successful authentication following brute-force activity
- Evidence of credential compromise
- Repeated attacks against multiple systems
- Suspicious activity from a known malicious source
- Evidence of persistence, lateral movement, or other post-compromise activity
- Impact to a critical or sensitive system

## 9. Analyst Documentation

Each investigation should record:

1. Alert signature
2. Timestamp
3. Source IP
4. Destination IP
5. Destination port/service
6. Severity and CVSS
7. CVE, when applicable
8. MITRE ATT&CK tactic and technique
9. Investigation findings
10. Recommended action
11. Escalation status

## 10. Evidence

The repository `screenshots/` directory contains Splunk dashboard and investigation evidence demonstrating the workflow in practice.

The investigation workflow is intentionally based on controlled lab telemetry and should not be interpreted as evidence of attacks against real-world systems.
