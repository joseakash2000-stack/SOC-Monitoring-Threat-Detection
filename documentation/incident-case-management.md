# SOC L1 Incident & Case Management Workflow

This extension adds a lightweight, portfolio-safe incident/case workflow to the Splunk SOC lab. It models how an L1 analyst moves a detection from alert intake through disposition, escalation, documentation, and closure.

> **Scope:** This is a simulated case-management workflow for a controlled lab. It is not a production ticketing system and does not claim integration with ServiceNow, Jira, or another ITSM platform.

## Analyst Workflow

```text
Splunk Alert
    ↓
Alert Intake
    ↓
Validate Detection
    ↓
True Positive / False Positive / Benign / Needs Investigation
    ↓
Investigate Source / Destination / Context
    ↓
Assign Severity
    ↓
Enrich + MITRE ATT&CK Mapping
    ↓
Create Incident Record
    ↓
Escalate When Criteria Are Met
    ↓
Document Findings / Actions
    ↓
Resolve / Close Case
```

## Alert Disposition

| Disposition | Meaning | Example |
|---|---|---|
| True Positive | Alert represents suspicious or policy-violating activity supported by available evidence | Repeated SSH brute-force behavior in the controlled lab |
| False Positive | Alert is generated by legitimate activity and the detection does not represent the intended threat condition after validation | A detection triggered by traffic that does not match the intended security scenario |
| Benign / Expected | Detection is technically valid but activity is intentionally generated or otherwise expected | Controlled PowerShell-to-CMD test activity |
| Needs Investigation | Evidence is insufficient to make a final disposition | Reconnaissance where authorization cannot be established from available telemetry |

## Minimum Case Record

Every investigated alert should capture:

- Case ID
- Alert timestamp
- Detection/signature
- Source IP
- Destination IP
- Destination port/service
- Initial severity
- True positive / false positive / benign / needs-investigation disposition
- Investigation summary
- MITRE ATT&CK context, when applicable
- Related alerts
- Recommended action
- Escalation decision
- Analyst notes
- Final status

## Escalation Criteria

Escalate when one or more of the following are supported by evidence:

1. Successful authentication follows repeated credential attacks.
2. Evidence suggests successful exploitation or host compromise.
3. Critical or high-severity activity targets an important system and cannot be dismissed as authorized activity.
4. Multiple related alerts indicate a broader attack sequence.
5. The analyst lacks sufficient authority or context to perform containment.

> A detection alone is not proof of compromise. Escalation should be based on the available evidence and the organization's incident-response procedure.

## Case Example — SSH Brute Force

**Case ID:** SOC-2026-001

**Detection:** `SOC DEMO - SSH Brute Force`

**Initial severity:** Critical

**Disposition:** True Positive — simulated attack activity

**MITRE ATT&CK:** T1110 — Brute Force

**Investigation summary:** Repeated SSH connection attempts from the simulated source were reviewed against the destination host and port 22. Related alert, flow, and SSH telemetry was correlated in Splunk. The available Suricata telemetry does not establish successful authentication or compromise, so authentication and endpoint logs would be required for confirmation.

**Escalation:** Escalate if successful authentication, suspicious post-authentication activity, or other evidence of compromise is identified.

**Recommended action:** Review authentication logs, correlate related activity, document findings, and follow the authorized containment/escalation process if malicious activity is confirmed.

**Final status:** Closed after investigation in the controlled lab.

## Case Example — Nmap Reconnaissance

**Case ID:** SOC-2026-002

**Detection:** `ET SCAN Possible Nmap User-Agent Observed`

**Initial severity:** Medium

**Disposition:** Needs Investigation

**MITRE ATT&CK:** T1046 — Network Service Discovery

**Investigation summary:** Repeated Nmap detections were correlated with additional activity from the same source. Source-wide correlation showed multiple distinct signatures, including vulnerability/exploit and SSH brute-force detections. The available Suricata telemetry cannot establish whether the scanning was authorized, so the case remains a reconnaissance investigation rather than being marked benign solely because it originated from the lab scanner.

**Escalation:** Escalate if the activity is unauthorized or if correlated evidence indicates malicious intent or compromise.

**Final status:** Closed after the available telemetry was documented; authorization and endpoint/service validation remain recommended follow-up actions.

## Case Example — Windows PowerShell to CMD

**Case ID:** SOC-2026-003

**Detection:** `PowerShell Spawned CMD`

**Initial severity:** Medium

**Disposition:** Benign / Expected

**MITRE ATT&CK:** T1059 — Command and Scripting Interpreter

**Investigation summary:** A controlled PowerShell-to-CMD execution was generated specifically to validate Windows Security Event ID 4688 process-creation telemetry. Splunk identified `powershell.exe` as the parent process and `cmd.exe` as the created process for user `Akash`. No malicious command line or compromise was established from the available evidence.

**Escalation:** No escalation for the controlled test. A real-world occurrence would require command-line, user, host, and surrounding endpoint/network context before classification.

**Final status:** Closed as expected test activity.
